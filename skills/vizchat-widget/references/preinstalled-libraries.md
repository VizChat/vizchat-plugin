# Dependencies and libraries shared with the host

Declare the third-party libraries you use under `dependencies` in `package.json` as usual; compilation bundles them into your widget (inline and nested alike). Each widget uses the version it
declares, so two widgets on the same canvas can use different versions of the same library without affecting each other. When you use the SDK's library wrapper subpaths (`@vizchat/widget-sdk/d3`, `/three`,
`/motion`, `/exact`), declare the matching library (`d3`, `three`, `motion`, `@cortex-js/compute-engine`) yourself as well.

Only the packages in the table below must share a single instance with the host and are not bundled:

| Library | Platform version | Purpose |
| --- | --- | --- |
| `react` | 19.2.8 | The host's React for inline widgets |
| `react-dom` | 19.2.8 | The host's React DOM for inline widgets |
| `zod` | 4.6.7 | Schema definitions |

Your declared range must cover the version in the table, or compilation fails; you can also only import these entry points of theirs (`react`, `react/jsx-runtime`, `react-dom/client`,
`zod`, `zod/mini` and so on) — any other subpath fails compilation too.

At publish time, an inline widget also produces a **self-contained build** (with the packages in the table bundled in).
If the host later moves one of those packages to a new major version that your declared range no longer covers, or the inline protocol
you built with is retired, the canvas switches to this self-contained build and runs it in its own iframe (running isolated); data,
operations and animations work as usual. Running isolated differs in two ways: popups that extend beyond the widget's frame (dropdown menus,
tooltips) are confined to the frame; the host's synchronous reads of elements inside the widget (following an element while dragging)
become asynchronous and lag one frame. The issues panel shows "N widgets are running isolated because of version incompatibility"; when
the user sees it, updating the dependencies and republishing restores normal running. You don't write any code for this; draft previews
always compile against the current host and never run isolated.

For `@vizchat/widget-sdk` and `@vizchat/ui` (the inline scaffold already writes them), write a `>=` lower bound, not `^`: compilation always uses the platform's latest set,
and your range only decides which version installs for local development. When a range does not cover the version the platform compiles with, `compile_widget` lists it under `warnings`:
your local type checks and tests are then running against a different version than the platform build.

## Dependency licenses

Dependency licenses are checked package by package at compile and publish time: permissive licenses such as MIT / BSD / Apache / ISC pass; MPL / EPL / CDDL pass, with the upstream source address added to the notices automatically;
GPL / AGPL, non-commercial licenses (CC-BY-NC and the like), source-available licenses (BUSL / SSPL / Elastic) and unrecognized licenses are rejected, and the error names the package and the reason. An LGPL library
cannot be bundled (readers must be able to swap it out): the compiler copies the single-file build its upstream publishes, unmodified, next to the bundle and loads it as a separate file. `p5` is supported today — declare it and
`import p5 from 'p5'` (import the package name itself, not a subpath), inline and nested alike; any other LGPL library, or an LGPL library pulled in by another dependency, fails compilation. The full license texts and copyright notices of the third-party packages bundled in are generated by the platform and shown under "Third-party licenses" on the widget's detail page; you don't write them yourself.

## Evaluating expressions from the snapshot

An expression in the snapshot (a `mathjs` expression) comes from the board's author and is evaluated in the viewer's canvas. Compile it with
`compileSafeExpression(math, expression)` from `@vizchat/widget-sdk/mathjs` (use `parseSafeExpression` before differentiating or simplifying), not
`math.compile` / `math.evaluate` directly: it rejects `import`, `config`, `evaluate`, `parse`, `simplify`, `derivative` and the like inside the expression,
and any index other than a number literal (`A[2]` is fine; `a.b`, `a["b"]`, `a[k]` are rejected), while your own code can still call those functions.

## Exact values

When a number field should accept exact values — fractions, roots, π (`"1/3"`, `"2*sqrt(2)"`, `"pi/4"`) — use `exactNumber({ min, max })` from
`@vizchat/widget-sdk/exact` instead of `z.number()`: the value is a number or a constant expression string, stored as written, and both forms
are range-checked by value. Read the number with `exactToNumber(value)`; show the exact form with `exactLatex(value)` (simplified LaTeX, or
`null` when it is not exact, cannot be simplified or is too long — then write the whole output as a decimal). To combine several values
(a product, a sum) build one expression with `exactProduct` / `exactSum` and pass it to `exactLatex`; `exactEquals` / `exactSign` compare
exactly. Parse a data editor's text input with `parseExactInput(raw, { min, max })`. Underneath is `@cortex-js/compute-engine` (declare it under `dependencies`);
the engine is only created when the first expression string turns up. To pin a LaTeX label to a point in an SVG chart, use
`appendSvgMathLabel(katex, parent, latex, { fontSize, color })` and its size estimate `estimateLatexSize` from `@vizchat/widget-sdk/katex`.

## Math in text

To typeset `$...$` in text the author writes (a problem, a step, a legend), use `katex` with the SDK's `MathText`: one in
`@vizchat/widget-sdk/react` and one in `/vue` (`<MathText katex={katex} text={…} />`); the plain function `renderMathText(katex, text)` is in
`@vizchat/widget-sdk/katex`. Add `import 'katex/dist/katex.min.css'` in the file that uses it — the styles and fonts ship with your widget,
inline or nested alike. It escapes the text around the math, shows a broken formula as written, and treats `\$` as a literal dollar sign;
don't paste `katex.renderToString` output into innerHTML yourself.
