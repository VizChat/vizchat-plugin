# Strings (i18n)

All user-visible strings go through `src/i18n/<language>.json`, never hard-coded. The interface supports seven languages — en, zh, es, fr, de, ja, ru — and each gets one file (the scaffold already creates them); a missing file fails the compile. Top-level keys are sections:

```json
{
  "viewState": { "empty": "No items yet", "untitled": "Untitled" },
  "config": {
    "display": {
      "_rjsf_title": "!Display",
      "_rjsf_description": "",
      "showValues": { "_rjsf_title": "Show values", "_rjsf_description": "Show each item's value" }
    }
  }
}
```

- Use: inline `useWidgetT('viewState')`, nested `ctx.t('viewState')`, then `t('empty')`; interpolation is written `{name}` and called as `t('greeting', { name })`.
  Write section names directly, with no prefix.
- The `config` section labels the property panel: every group and field in config needs an entry shaped `{ "_rjsf_title", "_rjsf_description" }`; a group title starting with `!`
  is expanded by default.
- Every language must have exactly the same keys. When you add or change a string, change all seven files together: write the language you are surest of first, then translate each of the others — don't leave old text in the other languages or copy the English over.
- Not in i18n: sample data in the default snapshot, and the `description` of ops and fields (written for agents, in English).

A missing translation does not error at runtime — the UI shows a key path like `widgets.<slug>.<section>.<key>` — so the compile gates catch it.
